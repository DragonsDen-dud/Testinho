# РАЗДЕЛ A — ОПРЕДЕЛЕНИЯ

| Термин | Значение |
|---|---|
| **Space (Пространство)** | Изолированный контейнер данных верхнего уровня (например, "Личное" и "Работа"). Каждое Пространство содержит свой независимый набор сфер жизни, привычек, задач, планов и диагностик. |
| **LifeDomain (Сфера жизни)** | Пользовательская категория внутри Пространства. Создаётся и переименовывается пользователем, никогда не хардкодится. |
| **TimeBlock (Временной блок)** | Пользовательский сегмент дня (по умолчанию Утро/День/Вечер, редактируется). |
| **Habit Strength (Сила привычки)** | Пропорциональный, экспоненциально затухающий показатель устойчивости привычки (0–100%), заменяющий бинарный "стрик". |
| **habitType** | `build` (формируемая привычка) или `avoid` (искореняемая привычка) — определяет полярность интерпретации чек-инов. |
| **Stake (Ставка/самоштраф)** | Условие, которое пользователь сам задаёт для привычки: при срабатывании триггера приложение фиксирует событие и предлагает признать выполнение самоналоженного обязательства. Никогда не исполняется автоматически. |
| **Critical Reminder** | Флаг на привычке/задаче, включающий генерацию `.ics`-файла для Apple/Google Calendar как резервный канал напоминаний. |
| **Scheduled AI Report** | Автоматически формируемый AI-инсайт по расписанию, генерируемый при следующем открытии приложения после наступления назначенного дня. |
| **Trash (Корзина)** | Хранилище мягко удалённых записей с окном восстановления. |
| **Someday List** | GTD-стиль список задач без дедлайна и активного статуса. |
| **Project** | Группа связанных задач с общим прогресс-баром. |
| **JournalEntry** | Свободная или по промпту запись в Дневнике, отдельно от лога привычек. |

# РАЗДЕЛ B — ФИЛОСОФИЯ И ГРАНИЦЫ ПРОЕКТА

### Статья 1. Природа продукта
STOA — не готовый трекер с зашитым набором категорий под конкретный образ жизни. Это **персональная операционная система**, каркас которой одинаков для любого пользователя, а содержание полностью определяется пользователем через конструктор (Раздел E.2). Ни одна строка кода не должна ссылаться на конкретные личные обстоятельства, интересы, профессию или сферы жизни пользователя — вся персонализация проходит через данные, а не через код.

### Статья 2. Приоритеты (в порядке убывания)
1. Скорость ежедневного взаимодействия (чек-ин ≤ 3 тапа).
2. Приватность и локальность данных по умолчанию.
3. Честность аналитики (без искусственной геймификации, без манипулятивных механик вовлечения).
4. Автономность от AI — базовый функционал работает полностью без интернета и без Claude API.
5. Расширяемость — архитектура должна выдерживать рост числа Пространств, привычек и задач без рефакторинга ядра.

### Статья 3. Принцип Config-Driven UI
Любая сущность, которую в наивной реализации можно было бы "зашить" (категории, временные блоки, шкала приоритета, язык интерфейса, тема), обязана быть строкой в базе данных, редактируемой пользователем через интерфейс, а не константой в коде.

# РАЗДЕЛ C — БАЗОВЫЕ АРХИТЕКТУРНЫЕ РЕШЕНИЯ (Статьи 4–19)

### Статья 4. Синхронизация данных — ОТКЛОНЕНО
Никакой облачной синхронизации основных данных. Один локальный экземпляр на iPhone (IndexedDB через Dexie.js). Единственные сетевые компоненты: прокси к Claude API и опциональный Telegram-канал напоминаний.

### Статья 5. Защита входа — ОТКЛОНЕНО
Без Face ID / кода доступа. Не проектировать заглушки авторизации "на будущее".

### Статья 6. Геймификация — ОТКЛОНЕНО
Никаких очков, уровней, бейджей, питомцев. Обратная связь при чек-ине — сдержанная.

### Статья 7. Apple Health / автотрекинг — ОТЛОЖЕНО, НЕ В MVP
Ручного ввода достаточно. HealthKit недоступен из чистого PWA без перехода на Capacitor — не оправдано на этом этапе.

### Статья 8. Мульти-контекст (Spaces) — ПРИНЯТО, ОБЯЗАТЕЛЬНО
Сущность `Space` верхнего уровня. Каждое Пространство содержит собственный независимый набор LifeDomain, TimeBlock, PriorityLevel, Habit, Todo, PlanEntry, DiagnosticEntry, North Star. Глобальными остаются только: язык, тема, ключ Claude API, расписание AI-отчёта, список Spaces, настройки бэкапа.

### Статья 9. Ставки (Stakes) — ПРИНЯТО, личный самоштраф-трекер
Пользователь сам задаёт условие триггера и текст обязательства. Приложение только логирует срабатывание и ждёт ручного подтверждения — никогда не исполняет ставку само (не двигает деньги, не блокирует другие приложения).

### Статья 10. Голосовой ввод — ПРИНЯТО
Кнопка микрофона в полях быстрого ввода через Web Speech API с обязательным feature-detection. Если API недоступен — кнопка скрывается полностью, пользователь использует системную диктовку iOS. Интегрируется минимум в: заметку к HabitLog, быстрое добавление Todo, JournalEntry.text, поле userFeedback в диагностике.

### Статья 11. Язык интерфейса — ПРИНЯТО: RU/EN переключатель
Полноценный i18n-слой. Все строки — в словарях, никаких строк напрямую в JSX.

### Статья 12. Scheduled AI Report — ПРИНЯТО, реализация "Check-on-Open"
Приложение проверяет при каждом запуске: наступил ли назначенный день и прошло ли достаточно времени с прошлого отчёта в текущем Space (для обоих scope — `week` и `month`, независимо друг от друга). Если да — автоматически генерируется `DiagnosticEntry` с `generatedBy: 'scheduled'`. Оговорка обязательна к отображению в настройках: отчёт формируется не точно по расписанию, а при следующем открытии приложения после назначенного момента — следствие local-first архитектуры без постоянного бэкенда.

### Статья 13. Календарь — ПРИНЯТО, одностороннее резервное напоминание
Не двусторонняя синхронизация, а генерация `.ics`-файла с `RRULE`/`VALARM` для привычек/задач с флагом `criticalReminder: true`, добавляемого пользователем в Календарь через нативный диалог iOS. Приложение никогда не читает данные обратно из Календаря. Одноразовая генерация — редактирование Habit/Todo впоследствии не обновляет уже добавленное событие автоматически.

### Статья 14. Тип привычки: build / avoid — ПРИНЯТО
`Habit.habitType: 'build' | 'avoid'`.
- Для `build`: Done = прогресс к цели.
- Для `avoid`: семантика инвертирована — "воздержался от вредного действия" = Done (успех), "сорвался" = Not done. Skip остаётся нейтральным.
- Habit Strength считается той же формулой (`score = score + α × (result − score)`), но для avoid-типа result вычисляется по инвертированной семантике.
- **UI-требование:** avoid-привычки визуально отличимы от build-привычек.

### Статья 15. Подзадачи в To-Do — ПРИНЯТО, опционально на уровне задачи
`Todo.subtasks?: { id, title, done }[]` — необязательное поле. По умолчанию задача создаётся плоской. Кнопка "Разбить на подзадачи" доступна по требованию. Прогресс отображается как `X/Y выполнено`.

### Статья 16. Структура AI-отчёта — ПРИНЯТО, гибридный подход
Два режима работы прокси-функции Claude API:
- `scheduled_template` — фиксированные секции: Сильные стороны / Слабые места / Конкретная стратегия на следующий период (2–3 пункта) / Сравнение с предыдущим периодом. Используется для Scheduled AI Report.
- `freeform_query` — ответ строится строго под заданный вопрос, без навязанной структуры. Используется для точечных вопросов пользователя.
- Оба режима используют одну и ту же агрегированную статистику (`autoStats`) как контекст.

### Статья 17. Хранение истории — ПРИНЯТО, бессрочно без архивации
`HabitLog`, `StakeEvent`, `DiagnosticEntry` хранятся вечно, без автоматического удаления или сжатия. Требование к коду: аналитика и графики обязаны использовать индексы Dexie по `date`/`habitId`/`spaceId` и агрегировать данные на уровне запроса, а не загружать всю историю в память.

### Статья 18. Резервное копирование — ПРИНЯТО, Вариант A (напоминание + один тап)
- `AppSettings.backup: { lastBackupExportedAt?, backupReminderIntervalDays }` (по умолчанию 30 дней).
- Полный JSON-экспорт всего состояния: `AppSettings` + все `Space` со всеми вложенными сущностями.
- Раз в заданный интервал, если реального экспорта не было — ненавязчивый баннер "Пора сделать бэкап" с кнопкой, запускающей экспорт + системное меню "Поделиться" (fallback на скачивание при отсутствии Web Share API).
- Импорт: **replace-all** — полная замена локального состояния импортированным, простое и безопасное поведение для однопользовательского локального приложения.
- Фото (Blob, см. Статью 23) кодируются в base64 внутри JSON при экспорте "с фото"; должна быть отдельная опция "без фото" для быстрого лёгкого бэкапа с явным предупреждением о размере файла в UI.

### Статья 19. Тон текста интерфейса — ПРИНЯТО, явная политика копирайта
Спокойный, точный, без лишних слов. Без мотивационных лозунгов и наигранного энтузиазма, но и без сухой канцелярщины.
Примеры: Хорошо — *"Пропущено 2 дня подряд."* / *"Сила привычки: 62%, снижается третью неделю."* Плохо — *"Ты справишься! 💪"* / *"Ура, ты сделал это!"*

# РАЗДЕЛ C-2 — РАСШИРЕННЫЕ РЕШЕНИЯ (Статьи 20–57)

## C-2.1 Жизненный цикл данных

### Статья 20. Мягкое удаление и Корзина
Habit, Todo, Project при удалении получают `deletedAt: string`, а не удаляются физически. Экран "Корзина" показывает все soft-deleted записи с кнопками "Восстановить" / "Удалить навсегда". Автоматическая физическая очистка — через `AppSettings.trashRetentionDays` (по умолчанию 30) дней после `deletedAt`.
**Требование к коду:** все списки и запросы (аналитика, дашборд, планирование, поиск) обязаны фильтровать `deletedAt == null` — soft-deleted записи не должны "просачиваться" в обычные экраны. Это встраивается в существующие CRUD с самого начала, а не retrofit-ится позже.
**Каскад при удалении Project:** пока Project находится в Корзине (soft-deleted, не спурджен) — `Todo.projectId` не трогается, UI показывает связанный проект как недоступный ("Проект удалён"). При окончательной очистке (авто-purge или ручное "Удалить навсегда") — `projectId` очищается у всех связанных Todo.

### Статья 21. Пауза/заморозка привычки
`Habit.pausedFrom?: string`, `Habit.pausedUntil?: string`. Во время паузы: привычка не участвует в ежедневном чек-ине (или показывается свёрнутой с пометкой "На паузе"), Habit Strength не пересчитывается (замораживается), напоминания не отправляются, дни паузы не засчитываются ни как `done`, ни как `not_done`.

### Статья 22. Заметки — простой текст
Поле `note` везде — обычная строка без Markdown/rich-text рендеринга.

### Статья 23. Фото-вложения
`HabitLog.photo?: Blob`, `Todo.photo?: Blob`, `JournalEntry.photo?: Blob` — хранятся как Blob напрямую в IndexedDB.
**Обязательное автосжатие:** перед сохранением — resize до ~1280px по длинной стороне, JPEG quality ~0.7.
**Влияние на экспорт:** JSON-экспорт с фото кодирует Blob в base64 — предупреждение о размере в UI, опция "без фото".

## C-2.2 Логика привычек

### Статья 24. Множественные записи в день для измеримых привычек
Для `measurable`-привычек `HabitLog.entries: { timestamp, value }[]`. `status = 'done'`, если `entries.length ≥ 1`. `bonus: boolean = entries.length ≥ 2` — нейтральный факт, **не очки и не награда** (не путать со Статьёй 6).

### Статья 25. Зависимости между привычками
`Habit.dependsOnHabitIds?: string[]`. Зависимая привычка отображается неактивной до выполнения предпосылок в этот же день. Валидация против циклических зависимостей (прямых, транзитивных, self-reference) при сохранении; "ромбовидные" зависимости (A зависит от B и C, оба зависят от D) — не цикл, не должны отклоняться.

### Статья 26. Локальные паттерн-инсайты (без AI)
Чисто локальный статистический модуль анализирует историю каждой привычки за 8 недель:
- **По дню недели:** "слабый день", если процент выполнения ниже среднего на ≥30 п.п. при ≥4 наблюдениях.
- **По времени дня:** только на основе реальных timestamp'ов логов (не на основе назначенного `timeBlockId`) — "сильное время", если один блок даёт заметно более высокий процент.
Отображается простой строкой на карточке привычки, попадает в `autoStats` для AI-отчёта.

### Статья 27. Отображение avoid-привычек — "дней без срыва"
Для `habitType: 'avoid'` на первом плане — счётчик "N дней без срыва", Habit Strength вторым. Для `build` — порядок обратный.

## C-2.3 Задачи и проекты

### Статья 28. Повторяющиеся задачи
`Todo.recurrence?: { type: 'daily'|'weekly'|'monthly'|'custom', params }`. Recurrence-задачи не участвуют в Habit Strength/стриках. При завершении — новый экземпляр создаётся с датой, рассчитанной от **исходной** `dueDate` завершённого экземпляра, а не от даты фактического завершения (позднее выполнение не должно сжимать следующий интервал).

### Статья 29. Временные слоты для задач
`Todo.scheduledTime?: string` (HH:mm). `TimeBlock.approxTimeRange?: { start, end }` (HH:mm каждое) — структурированное опциональное поле. Если у всех TimeBlock активного Space заданы диапазоны — Дневной план показывает единую слитную хронологическую шкалу (привычки + задачи вместе, отсортированные по времени). Если хотя бы один блок без времени — используется fallback из двух соседних групп (без падения и без частичного слияния).

### Статья 30. Умный reschedule и разбор просроченных
Кнопка "Перенести": *Завтра / Через неделю / Выбрать дату*. Баннер "N просроченных задач" показывается не чаще одного раза в календарный день (отслеживается по дате последнего показа, не по сессии) → экран "Разбор просроченных" с массовыми действиями (перенести все на сегодня / на завтра / разобрать по одной).

### Статья 31. Список "Когда-нибудь/Может быть"
`Todo.status` включает `'someday'`. Someday-задачи не имеют дедлайна, исключены из баннера просроченных и всех видов планирования. "Начать делать" требует назначения и `dueDate`, и `priorityLevelId` перед переходом в `'open'`.

### Статья 32. Простые проекты
`Project { id, spaceId, name, domainId?, color?, createdAt, archivedAt?, deletedAt? }`. `Todo.projectId?: string`. Прогресс-бар = % завершённых от незаархивированных задач. Один уровень иерархии, без вложенных подпроектов. `deletedAt` встроен с рождения сущности (не retrofit).

## C-2.4 Дневник (Journal)

### Статья 33. Модуль "Дневник"
```typescript
JournalPrompt { id, spaceId, text, active: boolean, sortOrder }
JournalEntry  { id, spaceId, date, promptId?: string, text: string, photo?: Blob, mood?: number, createdAt }
```
Стартовый редактируемый набор промптов (создаётся при создании **каждого** Space, включая последующие, не только при первичном онбординге):
1. "Что сегодня получилось хорошо?"
2. "Что было сложным?"
3. "На что я потратил время впустую?"
4. "За что я благодарен сегодня?"
5. "Что бы я сделал иначе?"
Свободный текст без привязки к промпту (`promptId = null`) тоже допустим. Голосовой ввод доступен.

## C-2.5 Аналитика и AI

### Статья 34. Кросс-Space аналитика — Phase 2, по умолчанию выключено
`AppSettings.crossSpaceOverviewEnabled: boolean` (default `false`). Опциональный экран с только агрегированным % по каждому Space — никогда не смешивает детальные данные разных Spaces.

### Статья 35. Корреляция привычка ↔ настроение
Для каждой привычки с ≥5 `done` и ≥5 `not_done` днями с заполненным `mood`: `avgMood(done) − avgMood(not_done)`, знак и одна десятичная. Для `avoid`-привычек — семантика перелейблена так, чтобы положительное число всегда означало "хорошее поведение коррелирует с лучшим настроением" (никогда не требовать от человека мысленно инвертировать знак). Build и avoid привычки с идентичными исходными данными должны давать структурно одинаковый (не противоположный по знаку) результат.

### Статья 36. AI-вопрос по конкретной привычке
Кнопка "Спросить Клода об этой привычке" на экране детали привычки — режим `freeform_query` с контекстом привычки, включая паттерны из Статьи 26.

### Статья 37. История AI-инсайтов
Экран "История AI-инсайтов" — хронологический список всех `DiagnosticEntry.aiInsight` активного Space.

### Статья 38. Управление стоимостью AI — честная политика
- `AppSettings.aiUsage: { callCount, currentPeriodStart, softCapWarningThreshold? }`.
- `AppSettings.aiModelPreference: { scheduledReport: 'haiku'|'sonnet', freeformQuery: 'haiku'|'sonnet' }` — default обе `haiku`.
- Видимый счётчик запросов в настройках, выбор модели явно виден пользователю.
- **Обязательная честная формулировка в UI:** по-настоящему бесплатного безлимитного тарифа не существует — ключ пользователя привязан к оплате по использованию.
- **Архитектурная граница (расширение Статьи 4):** только серверная прокси-функция обращается к `api.anthropic.com`. Клиент никогда не делает прямой fetch к Anthropic — постит на собственный прокси-эндпоинт, который прикрепляет ключ и модель на своей стороне.
- Прокси-эндпоинты обязаны иметь базовую защиту (ограничение origin и/или простой rate-limit) до публичного деплоя — открытый релей, который потребляет чужую квоту, недопустим.

## C-2.6 Уведомления

### Статья 39. Telegram — одностороннее
Резервный канал напоминаний строго односторонний (приложение → Telegram), без обратной отметки выполнения. Возможное будущее расширение, не в MVP.

### Статья 40. Эскалация напоминаний с состояниями реакции
`ReminderState { id, entityType: 'habit'|'todo', entityId, date, state, lastActionAt? }`. Состояния: `sent → (нет реакции в течение escalationWindowMinutes, default 45) → один повторный "мягкий" пинг (если не в тихие часы) → lapsed_for_day`. Реакции пользователя: `acknowledged` (залогировал), `snoozed` (+30/+60 мин), `dismissed` (явное "не сейчас" — немедленная остановка эскалации). **Жёсткий предел: максимум один повторный пинг в день на сущность** — не позволять бесконечную эскалацию.

### Статья 41. Тихие часы
`AppSettings.quietHours: { enabled, start, end }`. Уведомления внутри диапазона ставятся в очередь и доставляются сразу после `end` (если день ещё актуален), не пропадают молча и не отбрасываются задним числом на "вчера" без явной проверки на `enabled`.

### Статья 42. Утренний дайджест + индивидуальные напоминания
`AppSettings.morningDigest: { enabled, time }` — одно сводное уведомление ("Сегодня: N привычек, M задач"), полностью независимое от индивидуальных `reminderTimes`/`scheduledTime`. Обе системы включаются/выключаются раздельно.

**Ограничение архитектуры (зафиксировано явно):** доставка уведомлений реализована через браузерный Notification API, **foreground-only** — нет push-сервера (соответствует Статье 4: local-first без бэкенда). Напоминания прогрессируют только пока приложение открыто (поллер на активности Space + периодический опрос). Именно поэтому Статья 13 (Календарь) — не косметика, а единственный надёжный канал для `criticalReminder`-пунктов.

## C-2.8 Дополнительные функции

### Статья 48. Глобальный поиск
Поиск по ключевому слову по привычкам, задачам, Дневнику и диагностикам активного Space. Обязан исключать soft-deleted записи (та же дисциплина, что Статья 20).

### Статья 49. Плавающая кнопка быстрого добавления (FAB)
Единая кнопка "+", открывающая выбор: Привычка / Задача / Запись в Дневник — **всегда через реальный полноценный флоу создания**, никогда через урезанный параллельный путь. Если где-то уже существует более быстрый "quick-add" путь для одного из типов — оба сосуществуют явно разграниченными по назначению, не заменяя друг друга неявно.

### Статья 50. Undo-тост
После soft-delete (не после permanent purge) — тост на 5 секунд с кнопкой "Отменить", использующий тот же restore-механизм, что и Корзина, не отдельную реализацию.

### Статья 51. Автоматическая тема по системным настройкам iOS
Опция "Как в системе" (`theme.preset: 'system'`), следующая `prefers-color-scheme` живо, не только при загрузке.

### Статья 52. Онбординг — опциональные "примеры для вдохновения"
Кнопка "Показать примеры" — иллюстративные примеры, явно помеченные, никогда не сохраняются как реальные данные без явного ввода пользователя.

### Статья 53. Проверка целостности данных
Утилита в настройках, находящая осиротевшие ссылки (`HabitLog.habitId`, `Todo.projectId` и любые другие межсущностные ссылки в актуальной схеме) с ручным выбором действия на каждую находку (очистить ссылку / удалить запись). Enumerация таблиц — программная (как в механизме бэкапа), каталог самих *отношений* (foreign keys) может быть только ручным, так как Dexie не имеет нативного понятия внешнего ключа — это нужно явно проговорить, а не имитировать полную автоматичность.

### Статья 54. Базовая доступность (Accessibility)
**Статус: явно исключено из скоупа по решению Заказчика.** Dynamic Type, VoiceOver-подписи и контраст не реализуются в рамках этого контракта. Не возвращать эту статью в план без отдельного явного запроса.

### Статья 55. Экспорт истории одной привычки в CSV
Отдельно от полного JSON-бэкапа — CSV выгрузка полной истории `HabitLog` одной привычки.

### Статья 56. Экран "Что нового"
При смене версии приложения — один раз показывается экран с 2–3 пунктами изменений, не блокирующий. Новые установки не должны видеть этот экран как "непрочитанный" при первом запуске.

# РАЗДЕЛ E — ФУНКЦИОНАЛЬНЫЕ МОДУЛИ

### E.1 Пространства (Spaces)
Переключатель Пространств в верхней навигации, всегда виден. Создание нового Пространства запускает мини-онбординг (E.2) для этого конкретного Space, включая сидинг стартовых Дневник-промптов (Статья 33). Удаление/архивация Пространства требует подтверждения.

### E.2 Онбординг-конструктор (на уровне Space)
1. **Сферы жизни** — с нуля, без предзаполненных примеров (кроме опциональных "примеров для вдохновения", Статья 52).
2. **Временные блоки** — 3 по умолчанию (Утро/День/Вечер), редактируемое количество (1–6) и структурированное время (Статья 29).
3. **North Star** — опциональное поле, никогда не предполагается системой.
4. **Шкала приоритета задач** — по умолчанию Низкий/Средний/Высокий, редактируется.
Всё редактируется позже в Настройках → "Моя система".

### E.3 Привычки
CRUD с привязкой к LifeDomain, TimeBlock, `habitType`. Чек-ин в 3 тапа с инвертированной семантикой для avoid (Статья 14). Habit Strength + классический стрик. Опциональные `criticalReminder`, `stake`, `dependsOnHabitIds`, пауза (Статья 21), множественные записи для measurable (Статья 24). Локальные паттерн-инсайты (Статья 26) и корреляция с настроением (Статья 35) на карточке.

### E.4 To-Do / Completion List
Явно разделённые активный список и архив. Приоритет из пользовательской шкалы. Опциональные подзадачи (Статья 15), recurrence (Статья 28), `scheduledTime` (Статья 29), `someday`-статус (Статья 31). Быстрое добавление одной строкой с голосовым вводом.

### E.5 Планирование (день/неделя/месяц)
День: привычки по TimeBlock + задачи, слитая хронологическая шкала при наличии структурированного времени у всех блоков (Статья 29). Неделя: цветовая сетка. Месяц: тепловая карта. Свободный текстовый план на период.

### E.6 Аналитика
Dashboard по активному Space: % выполнения, средний Habit Strength по сферам (раздельно build/avoid), соотношение задач, корреляция настроения (Статья 35). Графики через Recharts с агрегацией на уровне запроса.

### E.7 Диагностика и AI-инсайты
Ручной запуск + автоматический по расписанию (обе cadence — week и month, независимо). Гибридная структура отчёта (Статья 16). North Star подключается только по явному тумблеру. История AI-инсайтов (Статья 37).

### E.8 Голосовой ввод
Кнопка микрофона с feature-detection, интегрирована в HabitLog.note, быстрое добавление Todo, JournalEntry.text, DiagnosticEntry.userFeedback.

### E.9 Проверка подключения (Connectivity Check)
Три независимых индикатора: Приложение · Интернет · Claude API. Pull-to-refresh (Статья 44) вручную перезапускает проверку.

### E.10 Резервные напоминания (Календарь)
Кнопка "Добавить в Календарь" для `criticalReminder`-пунктов — генерация `.ics` (Статья 13).

### E.11 Резервное копирование
Периодический баннер + мгновенный экспорт (Статья 18), с/без фото (Статья 23).

### E.12 Дневник
Отдельный таб. Список активных промптов (редактируемых) + свободная запись без промпта. Фото и голосовой ввод.

### E.13 Проекты
Список проектов активного Space, экран проекта со связанными задачами и прогресс-баром.

### E.14 Корзина
Список soft-deleted Habit/Todo/Project с восстановлением или окончательным удалением, авто-очистка по `trashRetentionDays`.

### E.15 Глобальный поиск
Единая строка поиска по привычкам, задачам, Дневнику, диагностикам активного Space, исключая soft-deleted записи.

### E.16 Быстрое добавление (FAB)
Плавающая кнопка на всех основных экранах, открывающая реальный флоу создания.

### E.17 Разбор просроченных задач
Экран с массовыми действиями по просроченным Todo.

### E.18 Настройки AI и стоимости
Счётчик запросов, выбор модели по типу вызова, честное предупреждение об отсутствии бесплатного тарифа.

### E.19 Доступность
**Исключено из скоупа (Статья 54). Не реализуется.**

# РАЗДЕЛ I — DEFINITION OF DONE

- [ ] Онбординг не содержит предзаполненных предположений о сферах жизни (кроме явно помеченных примеров, Статья 52).
- [ ] Все категории/блоки/приоритеты редактируются в UI без изменения кода.
- [ ] Переключение между Пространствами работает, данные изолированы корректно; новый Space получает свои стартовые Дневник-промпты.
- [ ] Ежедневный чек-ин — не более 3 тапов, инверсия для avoid корректна.
- [ ] Приложение полностью работает офлайн, кроме AI-кнопок и Telegram-резерва.
- [ ] Habit Strength считается пропорционально для build и avoid.
- [ ] Build и avoid привычки визуально различимы.
- [ ] Soft-delete работает для Habit/Todo/Project; Корзина восстанавливает и физически очищает по истечении срока; каскад на Project→Todo корректен на обеих стадиях (soft/purge).
- [ ] Пауза привычки корректно замораживает Habit Strength на всех типах расписания (включая `weekly_n_times`), не шлёт напоминаний.
- [ ] Зависимости блокируют чек-ин до выполнения предпосылки; циклы (включая транзитивные и self-reference) невозможны; "ромбовидные" зависимости корректно разрешены.
- [ ] Измеримая привычка засчитывается как `done` с одной записи; `bonus` — нейтральный факт.
- [ ] Recurring Todo регенерирует следующий экземпляр от исходной даты, не от даты позднего завершения.
- [ ] Просроченные задачи разбираются массовыми действиями; баннер — не чаще раза в календарный день.
- [ ] Someday-список отделён, promote-действие требует dueDate и priorityLevelId.
- [ ] Проект показывает корректный прогресс-бар.
- [ ] Дневник работает независимо от Диагностики.
- [ ] Локальные паттерн-инсайты вычисляются без AI и корректно передаются в отчёт.
- [ ] Корреляция настроение↔привычка вычисляется только при ≥5/≥5 данных, build/avoid дают структурно согласованный знак.
- [ ] AI-инфраструктура: прокси — единственная точка обращения к Anthropic; счётчик и честное предупреждение видны в настройках; оба scope (week/month) Scheduled Report работают независимо.
- [ ] Прокси-эндпоинты защищены базовым origin-check/rate-limit до публичного деплоя.
- [ ] Эскалация напоминаний не превышает одного повторного пинга в день; тихие часы соблюдаются корректно (без ложного ретроактивного повтора).
- [ ] Утренний дайджест и индивидуальные напоминания независимы друг от друга.
- [ ] Календарный `.ics`-экспорт корректен для мэппируемых типов расписания; немэппируемые (`weekly_n_times`, `custom`) явно отмечены, не имитированы.
- [ ] Голосовой ввод скрывается при отсутствии поддержки; ручное редактирование во время прослушивания не перезаписывается поздней транскрипцией.
- [ ] Глобальный поиск исключает soft-deleted записи по всем типам.
- [ ] FAB открывает полноценный флоу создания, не урезанный; сосуществование с любым существующим quick-add путём явно решено, а не оставлено конфликтующим.
- [ ] Undo-тост переиспользует механизм Корзины, не дублирует его.
- [ ] Полный JSON-бэкап покрывает 100% таблиц живой схемы (проверено программной enumерацией, не памятью), включая фото при выбранной опции; импорт восстанавливает состояние без потерь (включая сами Blob, не только их наличие).
- [ ] Проверка целостности данных находит осиротевшие записи по актуальному каталогу связей и даёт выбор действия на каждую.
- [ ] Экран "Что нового" показывается один раз на версию; новые установки не видят его как непрочитанный.
- [ ] Ни один пункт Раздела G не нарушен.
- [ ] Статья 54 (доступность) сознательно не реализована — это не пропуск, а явное решение.
