# STOA

A private, local-first companion for habits, tasks, and daily planning — implemented per the STOA v5.0 contract (`РАЗДЕЛ H`, core MVP scope).

Everything lives in this browser's IndexedDB (via Dexie). No account, no cloud sync.

## Stack

- React + TypeScript + Vite
- Tailwind CSS v4
- Dexie (IndexedDB) for local-first storage
- react-router-dom for navigation
- react-i18next for RU/EN localization
- vite-plugin-pwa for offline/installable support

## What's implemented (MVP foundation)

- **Spaces** — isolated top-level containers, switchable, with onboarding for the first Space + life domain (Article 8, E.1/E.2)
- **Habits** — build/avoid types, daily/weekly/custom schedules, measurable tracking with multiple entries per day and a neutral (non-gamified) bonus indicator, reminders, stakes (self-penalty, never auto-enforced), dependencies between habits (blocked with cycle detection on save), pause/freeze (Habit Strength frozen, hidden from check-in, no reminders), Habit Strength (proportional decaying 0–100%) and streak calculation, avoid-type "days without a slip" display (Articles 9, 14, 21, 24, 25, 27, E.3)
- **To-Do** — priorities, domains, optional subtasks (Article 15, E.4); recurrence (daily/weekly/monthly/custom, computed from the completed instance's own due date so a late completion never compresses the next interval, Article 28); scheduled time slots (Article 29); a Someday/Maybe list gated by a required due-date+priority prompt to promote back to Open (Article 31); smart reschedule (Tomorrow/In a week/Pick a date) and a dedicated overdue triage screen with bulk actions, plus a once-per-*calendar-day* (not once-per-session) overdue banner on Dashboard (Article 30)
- **Planning** — day plan notes linked to habits/tasks, plus a same-day timeline: a genuine single merged chronological sequence (habits at their TimeBlock's start time, tasks at their exact `scheduledTime`) once every TimeBlock in the Space has a structured time range set, falling back to the previous TimeBlock-grouped/scheduled-time-grouped two-section view for any Space that hasn't set times on all its blocks (E.5, Article 29)
- **Local pattern insights + mood correlation** — pure local computation, no AI: a weekday "weak day" flag when a habit's completion rate on one day-of-week sits ≥30 points below its own average with ≥4 observations of that weekday in the trailing 8 weeks; a time-of-day "strong time" flag computed only from measurable habits' real check-in timestamps (never guessed from the habit's assigned TimeBlock); and a signed mood correlation (`avgMood(done) − avgMood(not_done)`, relabeled but never sign-flipped for `avoid` habits) once a habit has ≥5 logged days on each side with mood set. Both patterns render as a single plain-language line on the habit card and are written into `DiagnosticEntry.autoStats`, one row per Space per week and per calendar month, for the Scheduled AI Report step to read as given facts (Articles 26, 35)
- **Dashboard** — today's habits and tasks, configurable module order (Article 45)
- **Settings** — language (RU/EN), theme (dark/light/high-contrast/system), Space management
- **Trash** — soft-delete for Habits/To-Do/Projects (`deletedAt`), Restore, permanent delete, and a 30-day auto-purge sweep on app start (Article 20, E.14). All active-item queries funnel through `listActiveHabits`/`listActiveTodos`/`listActiveProjects` in `src/data/`, so every screen — Dashboard, Planning, overdue banner — excludes trashed records from a single point rather than repeating the filter per query.
- **Projects** — simple one-level grouping for tasks with a progress bar (% done of active linked tasks), soft-deletable from creation like Habit/Todo (Article 32, E.13). Deletion is two-stage: while a Project sits in Trash, linked Todos keep their `projectId` untouched and show a "Project deleted" badge (restoring the Project silently reinstates the normal display); purging the Project (forever-delete or the retention sweep) cascades to clear `projectId` on every Todo that referenced it, since that's the point of no return for the reference too.
- **Journal** — its own bottom-nav tab, prompt-driven or free-text entries with optional mood, a fully editable starter set of 5 prompts seeded per Space (never hardcoded UI copy — DB records the user can edit/delete/add to from day one) (Article 33, E.12)
- **Mood capture** — an optional, non-blocking 5-point mood row appears beneath a habit right after a Done/Not done/Skip tap; the check-in itself is already saved the instant that button is tapped, so picking (or skipping, or later changing) a mood never delays or gates it. Toggleable off entirely in Settings (`moodCaptureEnabled`, on by default). This is what finally gives Article 35's mood correlation real usage data, closing the gap flagged in an earlier pass.
- **AI reports** — Claude-powered reflection, entirely bring-your-own-key (this is a local-first, no-account app, so there's no shared server-side key to hold): a `freeform_query` you can ask about any specific habit from its edit sheet, and a `scheduled_template` report that checks on every app open and generates itself — weekly, once past a configurable day-of-week, and monthly, once roughly 30 days have passed since the last one — each cadence independently toggleable in Settings, surfaced on Dashboard without a button press. Both call types are fed the already-computed Article 26/35 `autoStats` as given facts rather than asking the model to re-derive them from raw logs. An optional per-Space "North Star" statement can be attached to any single `freeform_query` call, but only when explicitly checked for that call — it resets after every ask, so it never silently carries into the next question (Articles 4, 12, 16, 38)
- **Reminders** — an optional mood row aside, actual reminder delivery for habits (`reminderTimes`) and tasks (`scheduledTime`), plus a once-daily digest. Quiet hours (Article 41) queue anything that would fire inside a configured window and deliver it right after the window ends, rather than dropping it — unless the day it was meant for is genuinely over, in which case it's silently skipped instead of showing up stale. Each reminder escalates at most once (Article 40): a follow-up nudge after 45 minutes of no action, then a hard stop for the day — logging the habit or completing the task acknowledges it automatically, and an inline "Reminder sent" row (`+30 min` / `+1 hr` / `Not now`) on the habit/task itself covers snoozing or dismissing by hand. The morning digest (Article 42) is a single independent toggle — turning it off never silences individual reminders, and vice versa (Articles 40, 41, 42)
- **Calendar export** — a one-way "Add to Calendar" action for any Habit or Todo with `criticalReminder` set, generating a real RFC 5545 `.ics` file client-side (structurally validated against an independent parser, `ical.js`, not just eyeballed). Habits map their `schedule` to a real calendar `RRULE` where the grammar allows a faithful mapping (`daily`, `specific_weekdays`); Todos are always a one-time event on `dueDate` (+ `scheduledTime` if set), never recurring even for a recurring Todo. Delivery prefers the Web Share API (what mobile browsers use to offer "Add to Calendar" from a share sheet) and falls back to a plain file download where sharing files isn't supported. This exists specifically because reminder delivery (Articles 40–42) is foreground-only — see the scope note there — so a critical reminder needs a channel that survives the app being closed (Article 13)
- **Voice input** — a mic button next to four text fields (habit check-in note, quick-add task title, journal entry, and a scheduled AI report's feedback field), transcribing on-device via the browser's own Web Speech API. Feature-detected once, centrally (`SPEECH_RECOGNITION_SUPPORTED`); the button simply doesn't exist anywhere in the DOM on a browser without it — no disabled state, no explanatory tooltip. Never sends audio or transcripts anywhere except the local text field it's attached to; a recognition failure of any kind (permission denied, no mic, a browser routing recognition through a server that's unreachable) fails silently back to plain typing, since the native keyboard's own dictation is always right there as the real fallback (Article 10)
- **Quick-add FAB** — a floating "+" on Dashboard/Habits/Todos/Journal opening a small Habit/Task/Journal entry menu, each option navigating to that screen's own real creation form (never a second, thinner implementation) via a shared `?new=1` convention each page already watches for (Article 49)
- **Global search** — a single search screen (also in the bottom nav) querying Habit names, Todo titles, Journal entries, and AI report text within the active Space, grouped by type; tapping a result opens that item's real screen. Reuses the same `listActiveHabits`/`listActiveTodos`-backed hooks every other screen uses, so soft-deleted records are excluded by construction rather than by a search-specific filter (Article 48)
- **Undo toast** — a 5-second "Deleted. [Undo]" toast after soft-deleting a Habit, Todo, or Project, calling the exact same restore function Trash's own "Restore" button uses. Letting it expire is equivalent to leaving the item in Trash — no separate action needed either way (Article 50)
- **System theme, live** — the `system` theme option follows the OS's own `prefers-color-scheme` continuously, no reload or in-app toggle needed. This one required no new code: it was already implemented entirely in CSS (`src/index.css`'s `@media (prefers-color-scheme: dark)` rule), which is inherently live by nature — verified with a Playwright pass that flips the emulated OS color scheme with no reload and confirms the rendered colors update instantly (Article 51)
- **Connectivity Check module, completed** — a three-status panel (App/Network/Claude API) on Dashboard, with pull-to-refresh manually re-running all three. Previously only the Claude-specific indicator existed (in Settings); "App" and "Network" checks are new (Article 44)
- **Home screen reorder** — a touch-friendly drag-to-reorder list in Settings for the persistent Dashboard sections (Habits, Todos), writing to the `homeScreenModuleOrder` field that already existed (Article 45)
- **Habit history CSV export** — exports one Habit's full `HabitLog` history (date, status, value/entries, note, mood) as a correctly-escaped CSV, from the habit's own edit sheet, via the same Share/download delivery Article 13 established (Article 55)
- **Full-database JSON backup** — a genuine export/import of everything: `AppSettings` plus every table this app's schema actually has right now, built generically over Dexie's own live table list rather than a hand-maintained one (see scope note below for why that matters here specifically). Import is destructive replace-all, confirmed before running. A Dashboard reminder banner nags after 30 days (configurable) since the last export, snoozable, clearing automatically the moment a real export happens (Article 18)
- **Photo attachments** — one optional photo on `HabitLog`, `Todo`, and `JournalEntry`, attached via the native `<input type="file" accept="image/*">` next to each entity's existing note/description/text field, with a thumbnail preview and a remove action. Every photo is resized to at most 1280px on its long edge and re-encoded as JPEG (~0.7 quality) client-side via canvas before it's ever written to IndexedDB — not an optional optimization, a hard requirement, since this local-first architecture has no server-side ceiling to catch uncontrolled photo growth (Article 23). The full-database backup (Article 18) now has a real photo path: an explicit "with photos" / "without photos" export choice, with a live estimated-size warning shown in the export UI itself once the estimate crosses 20 MB — see the scope note below for why that number
- **Data Integrity Check** — a user-triggered scan (Settings → "Check Database") for dangling foreign-key references anywhere in the local database — a `HabitLog` pointing at a deleted Habit, a `Todo` pointing at a purged Project, and every other real cross-entity reference this schema has. Each one found gets two explicit actions, never a silent auto-fix: clear just the dangling reference, or delete the orphaned record entirely. A soft-deleted-but-not-yet-purged record (still sitting in Trash) is correctly never flagged — it still exists, so nothing pointing at it is actually dangling (Article 53)
- **"What's New"** — a small, non-blocking, dismiss-once sheet that appears after an update, summarizing the 2–3 highlights of the current version from a manually maintained changelog. A brand-new install never sees it on its first session — only an existing install that's crossed a version boundary does (Article 56)
- **Analytics (E.6)** — a Space-scoped dashboard (`/analytics`, new bottom-nav entry) built on top of data that already existed: completion rate over 7/30/90-day trailing windows, average Habit Strength per domain split build/avoid, a task status breakdown, and per-habit mood correlation (Article 35) — the same computation reused, not re-derived. Charts render via Recharts (a new dependency — the spec calls for it explicitly and nothing in this app used a chart library before). Every chart card has an "Export as PNG" button (Article 46, un-deferred now that real charts exist — see the earlier scope note this replaces), converting the rendered SVG to a PNG client-side via canvas and reusing the same Share/download mechanism as CSV/.ics export. See the scope note below for the one genuinely underspecified point (the 7/30/90-day window framing) and how it was resolved

Deferred to later passes per the contract's build plan: Telegram reminders (see note below), cross-Space analytics (Article 34), and the remaining polish items in Section H.

### AI reports: deployment and scope notes

- **The proxy is real code, not yet a real deployment.** `api/ai-report.ts` and `api/ai-health.ts` are Vercel Edge Functions — the only things in this app that ever talk to `api.anthropic.com`. They work as committed once this repo is deployed to Vercel (zero extra config; Vercel auto-detects the `api/` folder). This sandbox has no deploy target and no real Anthropic key, so live verification this round used a small local mock server standing in for the proxy (same request/response contract), pointed at via `VITE_AI_PROXY_URL` — not committed, dev/test-only. Actually exercising a real Anthropic call is unverified until deployed.
- **Both proxy endpoints now enforce a basic origin allowlist and rate limit** (`api/_lib/security.ts`), closing the "unprotected public proxy" gap called out by the spec's own Section G item 19 / D.o.D checklist. Origin allowlisting reads `ALLOWED_ORIGINS` (comma-separated) from the Vercel project's environment variables — deliberately left unset in code rather than hardcoded, since no real deploy URL exists yet; set it once Step 3's deploy is live. A request with no `Origin` header at all (non-browser callers) is let through to the rate limiter rather than blocked outright, since there's nothing to check it against; any request that does carry an `Origin` header must match the allowlist, or gets `403 origin_not_allowed`. The rate limiter is a fixed-window, **in-memory-per-instance** counter (20 req/min on `ai-report`, 60 req/min on the free `ai-health` liveness check) — it resets on cold start or redeploy and isn't shared across concurrently-warm edge instances. That's a disclosed, accepted tradeoff for a single-user BYOK app (see the file's own comment); a real multi-tenant limit would need a shared store. Verified with real handler-level tests (`api/ai-report.test.ts`, `api/ai-health.test.ts`) that actually drive a mocked client past the cap and confirm `429`, and actually send a disallowed `Origin` and confirm `403` — not just that the code exists. `vercel dev` itself couldn't be run in this sandbox (no login credentials, same limitation as the real-Anthropic-key test in Step 3), so this is the strongest verification available here; a true edge-runtime smoke test remains open until a real deploy exists.
- **A real live-deploy bug was found and fixed in that origin check: the match was a bare strict-string comparison, not an origin-equality comparison.** `AppSettings.claudeApiKey` was entered on the real production deploy, `ALLOWED_ORIGINS` was set to (as far as anyone could visually confirm) the exact live origin, and a redeploy happened — yet real report calls still 403'd with `origin_not_allowed`, while `ai-health`'s liveness check reported "Connected." That split makes sense once you separate the two: `checkAiHealth()` issues a GET with no body, which browsers commonly send without an `Origin` header at all on a same-origin request; `callAiProxy()` issues a POST with a JSON body, which does get an `Origin` header per the Fetch spec even same-origin — so only the real report path ever exercised the check. `isOriginAllowed`/`corsHeaders` now compare origins via `new URL(x).origin` (RFC 6454 scheme+host+port equality — case-insensitive host, no trailing slash) on both sides instead of raw string equality, and `parseAllowedOrigins` strips surrounding quotes from a value (a common mistake when pasting into Vercel's env-var UI). Whichever of those it actually was couldn't be confirmed from this sandbox — it has no network path to the live deployment or Vercel's dashboard/logs (verified via the agent proxy's own policy-denial log for that host, not assumed) — so the fix covers every cosmetic mismatch this class of bug can produce rather than guessing at one. The `403` body also now echoes back the received `Origin` and the configured allowlist (non-secret, safe to expose) precisely so a future mismatch is diagnosable from the response itself instead of another blind round-trip.
- **The AI proxy's real error code was being discarded before it ever reached the screen.** `callAiProxy` (`src/lib/aiClient.ts`) already distinguished `origin_not_allowed` from `invalid_api_key` from `rate_limited` from a genuine network failure, but `AskAiHabitPanel` rendered the exact same static "Couldn't reach the AI service" copy for all of them, and nothing logged the real value anywhere — this is what made the live-deploy bug above undiagnosable without server log access in the first place. `callAiProxy` now `console.error`s the real status/error/detail on every failure path, and the panel shows the code inline next to the friendly message.
- **Each user brings their own Claude API key**, entered in Settings and stored in IndexedDB only (`AppSettings.claudeApiKey`) — never hardcoded, never logged. It travels with each request to our own proxy, which uses it for that one outbound call and never persists it server-side.
- **The Connectivity Check module (E.9) did not already exist.** It was referenced as already-shipped groundwork in an earlier assignment, but no such module — stub or otherwise — was present anywhere in the codebase before that pass. It's now built into the Settings → AI reports section (a small connected/unreachable indicator backed by `checkAiHealth()` against the proxy's own liveness endpoint, not a real Anthropic call).
- **North Star is a new, minimal addition**, not something that existed before it was needed. Article 16 assumes North Star content can be optionally attached, but nothing in the data model held such text — so `Space.northStar` (an optional free-text field, editable from Space edit) was added specifically so the opt-in toggle has real content to attach instead of being a no-op.
- **Week and month cadences are fully independent** (`AppSettings.scheduledAiReport.week`/`.month`), each with its own enabled flag and its own `DiagnosticEntry` row per period — one firing, failing, or being due never affects the other, verified explicitly with a test for both landing on the same app-open.

### Reminders: scope notes

- **Delivery is the browser's own Notification API, foreground-only.** This app has no push-notification backend and none was built — standing one up would mean holding subscriptions and a server that contradicts the app's own "local-first, no account" premise (see Article 4's AI proxy, which deliberately talks to nobody but Anthropic and holds nothing). Reminders, escalation, and the digest all run on a poller that only progresses while the app is actually open (once on activating a Space, then every minute) — nothing fires while the tab or app is closed. Telegram delivery remains fully deferred, as noted above; the door's left open for it since notify delivery is a single swappable function (`lib/notify.ts`), but nothing calls out to Telegram today.
- **`ReminderState` is one row per entity per day**, not per `reminderTime` — a habit with several reminder times in a day only ever gets one escalation cycle, anchored to whichever time is first found due.
- **Acknowledging is automatic, not a separate tap.** Logging a habit (done, not_done, or skip — any of the three, since all of them mean the user actually looked at it) or completing a task stops its escalation immediately; only snoozing and dismissing need an explicit tap, surfaced as a small inline row on the habit/task itself once a reminder is active.

### Calendar export: scope notes

- **`weekly_n_times` and `custom` habit schedules are not mapped to a calendar `RRULE`, and the button says so.** A quota like "3 times a week, any days" has no fixed day pattern — RRULE can only express a fixed recurrence, so picking any specific days to encode it would be a guess presented as fact, not a real mapping. The Add to Calendar action doesn't appear for those habits; a plain-language explanation does instead ("this schedule... doesn't have a fixed pattern of days"), never a silent guess and never a disabled button with no explanation.
- **This is strictly one-way and generate-once.** The app never reads anything back from Calendar, and editing the Habit or Todo afterward does not retroactively update an already-exported event — there's no live link between them at all. Re-triggering "Add to Calendar" produces a fresh file with the current data; it does not know about or touch whatever was added previously. This limitation is stated in the button's own UI copy, not just here.
- **An all-day Todo's alarm (no `scheduledTime` set) defaults to 9:00 local that day.** Not a spec ambiguity — Article 13 doesn't define a time for that case, so a fixed reasonable default was chosen rather than omitting the alarm entirely.
- **Verified against a real, independent iCalendar parser** (`ical.js`, dev-only, not a runtime dependency) rather than only against Vitest assertions written by the same logic being tested — every generated file for both schedule types, both Todo variants (timed and all-day), and text needing escaping parses cleanly and round-trips its `RRULE`/`VALARM`/`DTSTART` correctly.

### Voice input: scope notes

- **Three of the four target fields had no existing UI before this pass.** Article 10 named `HabitLog.note`, quick-add `Todo.title`, `JournalEntry.text`, and `DiagnosticEntry.userFeedback` as the four places to wire a mic button into. Only `JournalEntry.text` already had a text field (the Journal compose form); the other three fields existed in the data model but nothing wrote to them yet. Minimal UI was added for each — a progressive-disclosure note field on the habit card (shown once a check-in exists, mirroring the mood row), a one-line quick-add row on the Tasks screen (title only; open the full form for anything else), and a feedback textarea on the Scheduled AI Report banners — since "wire a mic button into this field" only makes sense once the field is reachable at all.
- **The exact stop-on-silence timing is not something this app configures or can guarantee.** With `continuous = false` (the standard single-utterance mode used here), when recognition decides you've stopped talking is entirely up to the browser/OS's own speech engine — there's no parameter in the Web Speech API to tune it. The mic button's own second-tap-to-stop is the only stop control this app actually owns.
- **The manual-edit-while-listening race is handled structurally, not just tested against.** A transcript is always merged onto the *current* field value via React's functional `setState` updater (`setValue(prev => appendTranscript(prev, transcript))`), so a manual edit made after listening started can never be clobbered by a transcript that resolves later — the merge always reads the latest state at the moment it lands, not a stale snapshot from when listening began.
- **Live verification used a mocked `SpeechRecognition`, not real audio.** This sandbox has no microphone or audio input device, so real speech couldn't be driven through Playwright. Verification instead used `page.addInitScript` to replace `window.webkitSpeechRecognition` with a fake implementation that fires a scripted `onresult` shortly after `start()` — close to how a real (non-continuous) recognizer would behave in a browser, but not the same as end-to-end audio-to-text. This drove the actual running app (real clicks, real React state, real Dexie writes) through all four wired locations, plus a separate real-Chromium check that the mic button is genuinely absent when `webkitSpeechRecognition` is deleted from `window` before the app loads.

### Quick-add FAB, quick-add row, and search: scope notes

- **The FAB and the Article 10 quick-add Todo row are deliberately kept as two separate, non-competing affordances, not merged.** The quick-add row (title-only, mic-enabled, lives on the Tasks screen) shipped as part of Article 10's four required mic locations; removing it now would silently break a reviewed requirement. Article 49 itself is explicit that the FAB must open "the same real creation flow each already has... not a stripped shortcut" — so the FAB's Task option can't just point at the quick-add row either, without violating its own spec. The resolution: the quick-add row stays as the fast, title-only path for when you're already on the Tasks screen; the FAB is the full-form path reachable from anywhere (Dashboard/Habits/Todos/Journal). They're differentiated by what they open, not duplicating each other.
- **No screen showed a historical `DiagnosticEntry` before this pass.** Dashboard only ever surfaces the *current* period's report banner; once a new week or month rotates in, the previous one was completely unreachable. Search needed a real destination for a diagnostic result, so a minimal read-only detail screen (`/diagnostics/:id`) was added — new scope, not a pre-existing screen being wired up. It shows the period, the AI insight (or a "not generated yet" empty state), and the same feedback field + mic button as the Dashboard banner.
- **Search is Space-scoped and reuses existing active-item hooks on purpose.** `useHabits`/`useTodos` are already backed by `listActiveHabits`/`listActiveTodos` (Article 20), so a soft-deleted Habit or Todo is excluded from search by construction — the search module never queries Dexie directly for those two types, specifically to avoid a second, independent place that could silently drift from the Trash exclusion rule. Journal entries and `DiagnosticEntry` rows have no soft-delete concept at all (Trash only covers Habit/Todo/Project), so nothing is filtered there.

### Article 44/45/51/55 batch: scope notes

- **Article 46 (export a chart as image) was skipped this round, by explicit agreement.** It assumes analytics charts already exist to attach an export button to — they don't. Every analytics insight in this app (weekday weak-day pattern, strong-time pattern, mood correlation) is a single plain-language text line, never a rendered SVG/chart, and no charting library is installed. Building a charting feature from scratch was judged out of scope for what the article describes as adding an export action.
- **Only one of the three "Connectivity Check" statuses existed before this round.** Settings had a Claude-API-specific indicator (Article 4); "App" (an IndexedDB round-trip) and "Network" (`navigator.onLine`) are new. `navigator.onLine` is a known-limited signal — it reflects whether the device believes it has a network route, not that any specific host is reachable — which is exactly why the separate Claude API check exists.
- **Article 55 references "the full JSON backup" as something to be separate from.** No such backup/export feature exists anywhere in this codebase (Article 18 was never implemented). The CSV export doesn't depend on it existing — it's fully self-contained.
- **There's no dedicated Habit "detail screen."** Same as Article 13's calendar export, the CSV export lives inside the existing HabitForm edit sheet (only when editing an existing habit), which is this app's closest equivalent.
- **The Share/download fallback (originally Article 13-only) was generalized** into `src/lib/shareOrDownload.ts` and is now used by both the `.ics` export and the CSV export, rather than each maintaining its own copy.

### Article 18 (full JSON backup): scope notes

- **Built against the live Dexie schema, not the original Section D contract, which is by now demonstrably behind reality.** This project's data model has drifted from Section D repeatedly as later Articles were implemented — `Space.northStar` (Article 16), the entire `ReminderState` table (Article 40, no Section D equivalent at all), the AI settings/usage fields (Article 38), `quietHours`/`morningDigest` (Articles 41/42), `homeScreenModuleOrder` (Article 45), and now the backup-reminder fields this Article added to `AppSettings` itself. A backup built by hand-listing "the entities from the spec" would have silently missed all of these. Instead, `buildBackupJson()` iterates `db.tables` — Dexie's own runtime list of whatever tables actually exist — so every table is included by construction, not by someone remembering to update an export list. A dedicated test (`src/lib/backup.test.ts`) diffs the live table list against what the export actually touches on every run, as a safety net against a future refactor accidentally reintroducing a hand-maintained list.
- **No photo/Blob data exists anywhere in this schema.** Article 18 describes a "with photos / without photos" export-size choice, which assumes Article 23 (photo attachments) already exists — it doesn't (still on the deferred list). There's nothing binary in any table to base64-encode, so that toggle isn't built; every table here is already plain JSON-serializable rows. Revisit this once Article 23 lands.
- **Replace-all, not merge**, per the article's own suggested default: importing a backup clears every table and repopulates it from the file, inside one transaction. A table present in the current schema but absent from an older backup file (e.g. `reminderStates` in a backup taken before Article 40 existed) just ends up empty after restore — the correct outcome for "nothing existed for it back then" — rather than being rejected.
- **The export file contains the Claude API key in plaintext** (`AppSettings.claudeApiKey`), same as it's already stored in plaintext in this device's IndexedDB — no new exposure is introduced by including it, but the Settings UI says so explicitly rather than leaving it a silent surprise.
- **A fresh device has to click through onboarding once before it can reach the Import button**, since every route in this app is gated behind `AppSettings.onboardingComplete` (App.tsx) with no exception for a first-run restore flow. That throwaway onboarding data is correctly wiped out by the subsequent import (verified live) — it's a minor extra step, not a bug, but a "Restore from backup" entry point on the onboarding welcome screen itself would remove it if that friction turns out to matter.

### Article 23 (photo attachments): scope notes

- **This closes a real gap two prior articles ran into.** Article 18 (backup) and Article 55 (CSV export) both referenced photo-related concepts (a "with/without photos" backup mode, "separate from the full JSON backup") that assumed Article 23 already existed — it didn't. This is the first drift this session found running in the opposite direction: the *contract* was ahead of the *implementation*, not behind it.
- **The Blob-aware backup export/import stays exactly as schema-generic as the rest of Article 18.** `buildBackupJson`/`restoreFromBackupJson` don't hold a list of "which tables have a photo field" — they walk each row's own fields at runtime and treat any value that's `instanceof Blob` as a photo, base64-encoding it (with-photos mode) or omitting the key entirely (without-photos mode). A future table with a Blob field needs zero changes to the backup code to be handled correctly, the same guarantee the rest of Article 18 already provides for ordinary fields.
- **The 20 MB size-warning threshold, stated explicitly as requested:** `PHOTO_BACKUP_WARNING_BYTES = 20 * 1024 * 1024` in `src/lib/backup.ts`. Reasoning: a compressed photo (1280px long edge, JPEG ~0.7 quality) typically lands around 150–250 KB; base64 inflates that by roughly another third. 20 MB of *estimated* export size corresponds to somewhere around 60–100+ photos — comfortably past "a few photos on a few entries" for a habit/journal app and into "this will take a moment to generate, download, or share." It's a warning shown in the export UI itself (a live, real estimate computed from the actual current data, not a fixed message), not a hard cap — the export still proceeds either way.
- **A genuine test-environment limitation was hit and worked around, not silently skipped.** `node-canvas` (the usual way to get real Canvas 2D support in Node/Vitest) requires native system libraries (`pangocairo`) not available in this sandbox — confirmed by a real failed `npm install`, not assumed. The compression function's pure resize-math (`computeTargetDimensions`) is fully Vitest-covered; the actual pixel decode/re-encode (`compressImage`, using `createImageBitmap` + `canvas.toBlob`) is verified live instead, in real Chromium, as part of this round's Playwright pass — see the live-verification results, not a Vitest report, for that proof.
- **A second, separate test-environment bug was found and fixed along the way, not worked around:** the original `blobToBase64` implementation used `FileReader`, a browser API Node.js doesn't implement. Testing it under `@vitest-environment jsdom` (which does have `FileReader`) surfaced a real interop gap — jsdom's own `Blob` implementation isn't recognized by the environment's native `structuredClone`, which `fake-indexeddb` relies on internally to clone values on insert, so a Blob silently became `{}` on every store/retrieve round-trip under jsdom specifically (confirmed directly with a throwaway debug test, not assumed — this does not happen in a real browser, where `Blob` and `structuredClone` are the same native implementation). Rewriting `blobToBase64` to use `Blob.arrayBuffer()` instead of `FileReader` removed the need for jsdom entirely — the fix isn't "avoid testing this," it's "don't depend on the one browser-only API this function never actually needed."

### Articles 53/56 (Data Integrity Check, What's New): scope notes

- **The foreign-key catalog is genuinely, unavoidably manual — stated explicitly rather than implied to be as automatic as Article 18's table enumeration.** `buildBackupJson()` can walk `db.tables()` generically because "every table" needs no relationship knowledge at all. "Every foreign key" fundamentally does: Dexie's schema strings only declare indexes, not which field points at which table, so there is nowhere at runtime to discover that from. `src/lib/integrityCheck.ts`'s `FK_RELATIONSHIPS` is a hand-written list of all 23 real cross-entity references in the current schema (every `spaceId`, every optional single reference like `Habit.domainId`, the two array references `Habit.dependsOnHabitIds` and `PlanEntry.linkedTodoIds`/`linkedHabitIds`, and the one polymorphic reference, `ReminderState.entityId`, which points at `habits` or `todos` depending on the row's own `entityType` — a branch impossible to express without app-level knowledge). What *is* kept generic is the scanner itself: it doesn't special-case any table by name, just walks the catalog and reads `db.table(name)` for whichever tables a given entry names. A new relationship needs one line added to the catalog, not new scanning code.
- **`StakeEvent.habitId`, named in the original assignment as an example orphan condition, does not exist.** No `StakeEvent` table or entity is anywhere in this codebase — a Habit's stake (Article 27) is an embedded field (`Habit.stake`), never a separate record with its own `habitId`, consistent with stakes being self-penalty and never auto-enforced (no event log of triggered stakes is kept at all). There was nothing to add a check for; this is not an omission.
- **A soft-deleted (Trashed, not yet purged) record is never flagged as an orphan.** The scan checks "does a record with this id exist in the target table at all," regardless of `deletedAt`/`archivedAt` — a `HabitLog` pointing at a Habit that's sitting in Trash for its 30-day retention window is pointing at a real, present record, exactly as designed (Article 20). Only a truly missing id (purged, or never valid) counts.
- **This scan is explicitly a safety net, not proof the Article 20 cascade-purge works.** `Todo.projectId` is cleared automatically when a Project is permanently deleted (existing, separately-tested behavior). A clean Data Integrity Check result says "nothing is currently dangling," not "the cascade logic is correct" — those are covered by the existing Article 20 tests, not this one.
- **The changelog is seeded, not backfilled.** Two entries exist (`src/lib/changelog.ts`) covering the two most recent user-facing batches of work; nothing earlier in this project's history was retroactively documented, since the article calls for a manually maintained list going forward, not a full history reconstruction.

### E.6 Analytics + Article 46: scope notes

- **The 7/30/90-day window framing for "% completion" is a judgment call, not a literal spec requirement — stated explicitly rather than presented as settled.** `SPEC.md`'s E.6 text ("% выполнения…") doesn't specify a window at all, only that graphs must aggregate at query level (Article 17). 7/30/90 days is a common, reasonable trend framing and was confirmed with the person driving this build before implementing it this way; `COMPLETION_WINDOWS` in `src/lib/analytics.ts` is the one place to change if a different framing is wanted later.
- **"% completion" is computed as one overall number per window, not split by domain or build/avoid.** Only Habit Strength is explicitly called out as "раздельно build/avoid" in the spec text — the completion-rate line item isn't, so it wasn't split further than the literal text asks for. Domain/type splits remain easy to add later; this is a reading of ambiguous spec text, not a technical limitation.
- **A habit's "today" only counts toward a completion window once it's actually logged**, exactly the same rule `habitStrength.ts`/`habitPatterns.ts` already use — an unstarted today isn't counted as a miss. This surprised the first draft of the analytics tests (which assumed today always counts), not the underlying implementation, which correctly inherited the existing convention.
- **Habit Strength by domain buckets habits with no `domainId` under an explicit `null` group** (rendered as "No domain"/"Без сферы"), rather than silently excluding them — a habit not yet assigned to a domain still has a Habit Strength worth showing.
- **`recharts` is a new dependency**, added specifically because E.6 calls for it by name and no charting library existed anywhere in this app before — this is also the reason Article 46 (export chart as PNG) was previously marked N/A: there were no charts to attach an export button to. That condition no longer holds, so Article 46 is implemented now, not deferred again.
- **Article 46's PNG export reuses the existing Share/download mechanism** (`src/lib/shareOrDownload.ts`, the same one CSV/.ics use) via a new `src/lib/chartExport.ts`: the rendered chart's `<svg>` is serialized, drawn onto a canvas (white background baked in, since a transparent PNG would be unreadable if the chart was rendered in dark theme and viewed elsewhere), and encoded as PNG client-side. This is browser-only (Image/canvas/XMLSerializer), the same category of limitation as `lib/imageCompression.ts` — it can't be meaningfully unit-tested under jsdom/Node in this sandbox. It was verified live instead: a Playwright pass actually clicked the export button, captured the downloaded file, decoded its pixels in a real browser canvas, and confirmed the PNG genuinely contains chart colors (109k+ non-white pixels), not a blank/transparent image — a stronger check than confirming a file merely got produced.
- **A CSS-`var()`-in-SVG-attribute resolution question came up during verification and was resolved by checking the real output, not a proxy for it.** `getComputedStyle(svgPath).fill` returned an empty string in headless Chromium even though the element correctly renders in color — that API is not a reliable signal here. The actual exported PNG's decoded pixels are what settled it (see above); charts use `var(--stoa-accent)` etc. directly so they stay correct across live theme switches (Article 51) without any separate theme-detection logic in the chart code.
- **Mood correlation on this dashboard is a thin aggregation wrapper, not new logic.** It calls the existing `computeMoodCorrelation` (Article 35) once per habit and only lists habits that clear its existing ≥5/≥5 sample threshold — habits below that threshold are simply absent from the chart, with an empty-state message shown only when zero habits qualify at all.

### Icon pickers (Space vs. LifeDomain): scope notes

- **No data migration was needed for either change.** `Space.icon` and `LifeDomain.icon` (`src/db/types.ts`) were already plain `string` fields, not an enum or union type — the "preset-only" behavior was purely a UI constraint (`SwatchPicker` only rendering buttons for `PRESET_ICONS`), never a data-model one. An icon picked under the old preset-only UI is stored as the same plain string a free-typed emoji would be, so existing Spaces/LifeDomains render and edit identically either way — verified live by seeding a domain with a preset-era icon, confirming it displays correctly, and confirming its edit form pre-fills the existing value correctly into the new free-text field.
- **The two fields got different treatments on purpose, per explicit instruction:** `LifeDomain.icon` now uses a new `EmojiInput` (free-text — the user brings up their own keyboard's emoji key, same as any other text field; there's no special HTML attribute that forces an emoji-only keyboard) in all three places it's edited (`DomainsPage`, and both the Space-creation and Domain-creation steps of onboarding — the onboarding domain step was using the same preset picker and needed the same swap for consistency, since it edits the identical field). `Space.icon` keeps `SwatchPicker` unchanged; `PRESET_ICONS` (`src/lib/presets.ts`) just gained 5 entries (🏃✈️🎮🌍👪) appended after the original 10, in the same order, so nothing already relying on those values changes.
- **`presets.test.ts`** locks in that the original 10 `PRESET_ICONS` stay in their original order (not just present-somewhere) and that exactly 5 new, non-duplicate entries were added — a regression guard against a future edit silently reordering or trimming the preset list.

### Scheduled AI Report relocation (Dashboard banner → Analytics): scope notes

- **Article 12's generation logic is completely untouched** — `runScheduledReportsIfDue`, the check-on-open due math, and both `upsertWeeklyAutoStats`/`upsertMonthlyAutoStats` are unchanged. Only where and how the user finds out a report exists changed: a banner that appeared on every Dashboard visit during a report's period, unconditionally, became a small dot on the Analytics nav tab that clears once actually viewed.
- **`DiagnosticEntry.viewedAt?: string`** is new — undefined means never viewed. Set once, on first view, by `markDiagnosticViewed` (`src/data/diagnostics.ts`), which is a deliberate no-op if already set, so revisiting Analytics repeatedly (or triggering the mark-viewed effect again on a feedback-field re-render) never bumps a report's "viewed" moment forward.
- **"Viewed" means "visible on Analytics," not a separate click.** `AnalyticsPage` runs a `useEffect` that marks the current week/month report viewed as soon as it renders — matching how the old banner needed no interaction beyond being on screen. The report *section* itself doesn't disappear once viewed (unlike the old banner, which had a dismiss button); it stays for the rest of its period so the user can come back and re-read it, same permanence `DiagnosticDetailPage` already gives an older report reached via search. Only the *nav badge* is the transient part.
- **The badge (`useHasUnviewedScheduledReport`, `src/state/useDiagnostics.ts`) is deliberately scoped to the same "current period" query `useCurrentScheduledReport` already used**, not "any unviewed report ever generated." That's what guarantees the badge always clears on a visit to Analytics: the badge and the report section look at exactly the same rows, so nothing can go stale/unreachable behind a badge that never turns off. A broader "any unviewed, any period" query would have this exact failure mode the moment a report's period rotates out before being viewed.
- **`ScheduledReportBanner.tsx` (Dashboard) was deleted, not deprecated in place** — replaced by `ScheduledReportCard.tsx` (Analytics), which is the same report-display markup minus the dismiss button (dismissal is no longer a concept; viewing replaces it). No component tried to serve both call sites at once, since the interaction models (ephemeral popup vs. permanent section) are different enough that forcing one component to do both would've meant a dismiss prop that's sometimes meaningless.
- **Verified live**, not just by reading the code: seeded a real weekly `DiagnosticEntry` (`generatedBy: 'scheduled'`), confirmed no banner/report text anywhere on Dashboard, confirmed the badge appears on the Analytics tab, confirmed the report's actual AI-insight text (not just charts) renders on Analytics, confirmed the badge clears and `viewedAt` persists after visiting, then seeded a second, independent monthly report and confirmed the badge reappears and clears independently of the already-viewed weekly one — the exact scenario the assignment's verification checklist called out.

### Explicit feedback save + prior-period AI context: scope notes

- **`DiagnosticEntry.userFeedback` persistence is now Save-button-only, for both typed and voice-transcribed text.** Previously it autosaved on blur, and a voice transcript wrote straight through on every chunk — the button would have been decorative on top of that. Both paths (`onChange` and `MicButton.onTranscript`) now only update local draft state; `FeedbackField` (`src/components/diagnostics/FeedbackField.tsx`) is the one place that ever calls `updateDiagnosticFeedback`, and only in response to the Save button being clicked.
- **One shared component, not two copies.** `ScheduledReportCard` (Analytics) and `DiagnosticDetailPage` (an older report reached via search) both had their own independent feedback-editing block before this — exactly the kind of duplicated-instance drift already caught twice this session (the onboarding domain-icon picker). Both now render `<FeedbackField key={entry.id} entryId={...} initialValue={...} />`; the `key` matters — without it, navigating between two different DiagnosticDetailPage entries wouldn't reset the component's internal draft/dirty state, since the id changing alone doesn't remount a child with no key tied to it.
- **Dirty-state tracking is a plain string comparison** (`feedback.trim() !== lastSaved`), not a boolean flag toggled imperatively — so it can't drift out of sync with the actual draft text the way a hand-maintained flag could (e.g. forgetting to clear it on some edit path). Editing again after a save is handled by this same comparison naturally going true again; no special-case "was this a re-edit" logic was needed.
- **Prior-period feedback retrieval (`getPriorPeriodFeedback`, `src/data/aiReports.ts`) only looks at the single most recent prior entry**, not the most recent one *with* feedback. If that entry's feedback is empty but an older one has some, nothing is included — a literal reading of the assignment's spec, and arguably the more defensible one: reaching further back risks resurfacing a reflection from a period the user may not even remember, attributed to "the previous period."
- **`generatedBy` is intentionally not filtered** in that lookup — a `manual` (freeform_query) entry's feedback is exactly as eligible as a `scheduled` one's, per the assignment's explicit instruction. `reportType` isn't filtered either, for the same reason, though in practice a `freeform_query` entry only ever has `scope: 'week'` (see `runFreeformQuery`), so it's never eligible as month-scope prior context.
- **Judgment call, as requested: where the prior-feedback block sits in the prompt.** It's placed immediately after the `autoStats` block and before North Star (`src/lib/aiPrompts.ts`). Reasoning: prior feedback is about the same reporting cycle the "Comparison to previous period" section directly concerns, a tighter tie to this call's purpose than North Star's broader, rarer, opt-in identity/goals context — so it reads as closely-related context for the model, not a late addendum after an unrelated block.
- **`priorFeedback` is reportType-gated in `buildUserMessage`, not just caller-gated.** Nothing currently calls it with `priorFeedback` set for `freeform_query` (only `generateScheduledReport` ever passes it, and always with `reportType: 'scheduled_template'`), but the prompt-builder itself still won't include the block unless `reportType === 'scheduled_template'` — the same defense-in-depth pattern this file already uses for North Star's opt-in gating, not relying on caller discipline alone.
- **Verified live, with the network payload actually inspected, not just the database:** intercepted the real outbound `/api/ai-report` request via Playwright route interception (this sandbox still has no path to a real Anthropic call), seeded a prior week's `DiagnosticEntry` with feedback, triggered the real check-on-open flow, and confirmed the captured request body's `context.priorFeedback` contained that exact text — not merely that it was in IndexedDB. Also verified end-to-end: typed new feedback into a live generated report, clicked Save, saw the "Saved" confirmation, reloaded the page, and confirmed the text was still there.

### Standing gotcha: PWA cache staleness can look exactly like an unshipped fix

This app is a PWA (`registerType: 'autoUpdate'`, precaches everything — see `vite.config.ts`). A device that already has it open/installed can keep serving the old service-worker-cached build for a while after a real fix has been committed, deployed, and verified correct in source — this has already happened once (the Space icon picker report: code was correct on the pushed commit, a redeploy had happened, and the report still initially looked like a regression until the app was fully closed and reopened, not just reloaded/pulled-to-refresh). Before treating a "this looks unfixed" report as a real regression: confirm a redeploy actually happened after the fix commit, and have the report try a full close-and-reopen (or removing/re-adding the Home Screen icon on iOS) — a plain in-app refresh is not always enough to pick up a new service worker. This applies symmetrically to live-verification work done from this end too: testing this app in a way that persists a service worker across sessions (rather than a fresh `npm run dev` process, which has none) risks the same staleness affecting the verification itself.
