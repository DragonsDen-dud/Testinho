# STOA

A private, local-first companion for habits, tasks, and daily planning — implemented per the STOA v5.0 contract (`РАЗДЕЛ H`, core MVP scope).

Everything lives in this browser's IndexedDB (via Dexie). No account, no cloud sync.

## Stack

- React + TypeScript + Vite
- Tailwind CSS v4
- Dexie (IndexedDB) for local-first storage
- react-router-dom for navigation
- react-i18next for RU/EN localization
- vite-plugin-pwa for offline/installable support

## What's implemented (MVP foundation)

- **Spaces** — isolated top-level containers, switchable, with onboarding for the first Space + life domain (Article 8, E.1/E.2)
- **Habits** — build/avoid types, daily/weekly/custom schedules, measurable tracking with multiple entries per day and a neutral (non-gamified) bonus indicator, reminders, stakes (self-penalty, never auto-enforced), dependencies between habits (blocked with cycle detection on save), pause/freeze (Habit Strength frozen, hidden from check-in, no reminders), Habit Strength (proportional decaying 0–100%) and streak calculation, avoid-type "days without a slip" display (Articles 9, 14, 21, 24, 25, 27, E.3)
- **To-Do** — priorities, domains, optional subtasks (Article 15, E.4); recurrence (daily/weekly/monthly/custom, computed from the completed instance's own due date so a late completion never compresses the next interval, Article 28); scheduled time slots (Article 29); a Someday/Maybe list gated by a required due-date+priority prompt to promote back to Open (Article 31); smart reschedule (Tomorrow/In a week/Pick a date) and a dedicated overdue triage screen with bulk actions, plus a once-per-*calendar-day* (not once-per-session) overdue banner on Dashboard (Article 30)
- **Planning** — day plan notes linked to habits/tasks, plus a same-day timeline: a genuine single merged chronological sequence (habits at their TimeBlock's start time, tasks at their exact `scheduledTime`) once every TimeBlock in the Space has a structured time range set, falling back to the previous TimeBlock-grouped/scheduled-time-grouped two-section view for any Space that hasn't set times on all its blocks (E.5, Article 29)
- **Local pattern insights + mood correlation** — pure local computation, no AI: a weekday "weak day" flag when a habit's completion rate on one day-of-week sits ≥30 points below its own average with ≥4 observations of that weekday in the trailing 8 weeks; a time-of-day "strong time" flag computed only from measurable habits' real check-in timestamps (never guessed from the habit's assigned TimeBlock); and a signed mood correlation (`avgMood(done) − avgMood(not_done)`, relabeled but never sign-flipped for `avoid` habits) once a habit has ≥5 logged days on each side with mood set. Both patterns render as a single plain-language line on the habit card and are written into `DiagnosticEntry.autoStats`, one row per Space per week and per calendar month, for the Scheduled AI Report step to read as given facts (Articles 26, 35)
- **Dashboard** — today's habits and tasks, configurable module order (Article 45)
- **Settings** — language (RU/EN), theme (dark/light/high-contrast/system), Space management
- **Trash** — soft-delete for Habits/To-Do/Projects (`deletedAt`), Restore, permanent delete, and a 30-day auto-purge sweep on app start (Article 20, E.14). All active-item queries funnel through `listActiveHabits`/`listActiveTodos`/`listActiveProjects` in `src/data/`, so every screen — Dashboard, Planning, overdue banner — excludes trashed records from a single point rather than repeating the filter per query.
- **Projects** — simple one-level grouping for tasks with a progress bar (% done of active linked tasks), soft-deletable from creation like Habit/Todo (Article 32, E.13). Deletion is two-stage: while a Project sits in Trash, linked Todos keep their `projectId` untouched and show a "Project deleted" badge (restoring the Project silently reinstates the normal display); purging the Project (forever-delete or the retention sweep) cascades to clear `projectId` on every Todo that referenced it, since that's the point of no return for the reference too.
- **Journal** — its own bottom-nav tab, prompt-driven or free-text entries with optional mood, a fully editable starter set of 5 prompts seeded per Space (never hardcoded UI copy — DB records the user can edit/delete/add to from day one) (Article 33, E.12)
- **Mood capture** — an optional, non-blocking 5-point mood row appears beneath a habit right after a Done/Not done/Skip tap; the check-in itself is already saved the instant that button is tapped, so picking (or skipping, or later changing) a mood never delays or gates it. Toggleable off entirely in Settings (`moodCaptureEnabled`, on by default). This is what finally gives Article 35's mood correlation real usage data, closing the gap flagged in an earlier pass.
- **AI reports** — Claude-powered reflection, entirely bring-your-own-key (this is a local-first, no-account app, so there's no shared server-side key to hold): a `freeform_query` you can ask about any specific habit from its edit sheet, and a `scheduled_template` report that checks on every app open and generates itself — weekly, once past a configurable day-of-week, and monthly, once roughly 30 days have passed since the last one — each cadence independently toggleable in Settings, surfaced on Dashboard without a button press. Both call types are fed the already-computed Article 26/35 `autoStats` as given facts rather than asking the model to re-derive them from raw logs. An optional per-Space "North Star" statement can be attached to any single `freeform_query` call, but only when explicitly checked for that call — it resets after every ask, so it never silently carries into the next question (Articles 4, 12, 16, 38)
- **Reminders** — an optional mood row aside, actual reminder delivery for habits (`reminderTimes`) and tasks (`scheduledTime`), plus a once-daily digest. Quiet hours (Article 41) queue anything that would fire inside a configured window and deliver it right after the window ends, rather than dropping it — unless the day it was meant for is genuinely over, in which case it's silently skipped instead of showing up stale. Each reminder escalates at most once (Article 40): a follow-up nudge after 45 minutes of no action, then a hard stop for the day — logging the habit or completing the task acknowledges it automatically, and an inline "Reminder sent" row (`+30 min` / `+1 hr` / `Not now`) on the habit/task itself covers snoozing or dismissing by hand. The morning digest (Article 42) is a single independent toggle — turning it off never silences individual reminders, and vice versa (Articles 40, 41, 42)
- **Calendar export** — a one-way "Add to Calendar" action for any Habit or Todo with `criticalReminder` set, generating a real RFC 5545 `.ics` file client-side (structurally validated against an independent parser, `ical.js`, not just eyeballed). Habits map their `schedule` to a real calendar `RRULE` where the grammar allows a faithful mapping (`daily`, `specific_weekdays`); Todos are always a one-time event on `dueDate` (+ `scheduledTime` if set), never recurring even for a recurring Todo. Delivery prefers the Web Share API (what mobile browsers use to offer "Add to Calendar" from a share sheet) and falls back to a plain file download where sharing files isn't supported. This exists specifically because reminder delivery (Articles 40–42) is foreground-only — see the scope note there — so a critical reminder needs a channel that survives the app being closed (Article 13)

Deferred to later passes per the contract's build plan: photo attachments (Article 23), Telegram reminders (see note below), voice input, cross-Space analytics, and the remaining polish items in Section H.

### AI reports: deployment and scope notes

- **The proxy is real code, not yet a real deployment.** `api/ai-report.ts` and `api/ai-health.ts` are Vercel Edge Functions — the only things in this app that ever talk to `api.anthropic.com`. They work as committed once this repo is deployed to Vercel (zero extra config; Vercel auto-detects the `api/` folder). This sandbox has no deploy target and no real Anthropic key, so live verification this round used a small local mock server standing in for the proxy (same request/response contract), pointed at via `VITE_AI_PROXY_URL` — not committed, dev/test-only. Actually exercising a real Anthropic call is unverified until deployed.
- **Each user brings their own Claude API key**, entered in Settings and stored in IndexedDB only (`AppSettings.claudeApiKey`) — never hardcoded, never logged. It travels with each request to our own proxy, which uses it for that one outbound call and never persists it server-side.
- **The Connectivity Check module (E.9) did not already exist.** It was referenced as already-shipped groundwork in an earlier assignment, but no such module — stub or otherwise — was present anywhere in the codebase before that pass. It's now built into the Settings → AI reports section (a small connected/unreachable indicator backed by `checkAiHealth()` against the proxy's own liveness endpoint, not a real Anthropic call).
- **North Star is a new, minimal addition**, not something that existed before it was needed. Article 16 assumes North Star content can be optionally attached, but nothing in the data model held such text — so `Space.northStar` (an optional free-text field, editable from Space edit) was added specifically so the opt-in toggle has real content to attach instead of being a no-op.
- **Week and month cadences are fully independent** (`AppSettings.scheduledAiReport.week`/`.month`), each with its own enabled flag and its own `DiagnosticEntry` row per period — one firing, failing, or being due never affects the other, verified explicitly with a test for both landing on the same app-open.

### Reminders: scope notes

- **Delivery is the browser's own Notification API, foreground-only.** This app has no push-notification backend and none was built — standing one up would mean holding subscriptions and a server that contradicts the app's own "local-first, no account" premise (see Article 4's AI proxy, which deliberately talks to nobody but Anthropic and holds nothing). Reminders, escalation, and the digest all run on a poller that only progresses while the app is actually open (once on activating a Space, then every minute) — nothing fires while the tab or app is closed. Telegram delivery remains fully deferred, as noted above; the door's left open for it since notify delivery is a single swappable function (`lib/notify.ts`), but nothing calls out to Telegram today.
- **`ReminderState` is one row per entity per day**, not per `reminderTime` — a habit with several reminder times in a day only ever gets one escalation cycle, anchored to whichever time is first found due.
- **Acknowledging is automatic, not a separate tap.** Logging a habit (done, not_done, or skip — any of the three, since all of them mean the user actually looked at it) or completing a task stops its escalation immediately; only snoozing and dismissing need an explicit tap, surfaced as a small inline row on the habit/task itself once a reminder is active.

### Calendar export: scope notes

- **`weekly_n_times` and `custom` habit schedules are not mapped to a calendar `RRULE`, and the button says so.** A quota like "3 times a week, any days" has no fixed day pattern — RRULE can only express a fixed recurrence, so picking any specific days to encode it would be a guess presented as fact, not a real mapping. The Add to Calendar action doesn't appear for those habits; a plain-language explanation does instead ("this schedule... doesn't have a fixed pattern of days"), never a silent guess and never a disabled button with no explanation.
- **This is strictly one-way and generate-once.** The app never reads anything back from Calendar, and editing the Habit or Todo afterward does not retroactively update an already-exported event — there's no live link between them at all. Re-triggering "Add to Calendar" produces a fresh file with the current data; it does not know about or touch whatever was added previously. This limitation is stated in the button's own UI copy, not just here.
- **An all-day Todo's alarm (no `scheduledTime` set) defaults to 9:00 local that day.** Not a spec ambiguity — Article 13 doesn't define a time for that case, so a fixed reasonable default was chosen rather than omitting the alarm entirely.
- **Verified against a real, independent iCalendar parser** (`ical.js`, dev-only, not a runtime dependency) rather than only against Vitest assertions written by the same logic being tested — every generated file for both schedule types, both Todo variants (timed and all-day), and text needing escaping parses cleanly and round-trips its `RRULE`/`VALARM`/`DTSTART` correctly.

## Development

```bash
npm install
npm run dev      # start dev server
npm run build    # typecheck + production build
npm run lint      # oxlint
npm run test      # vitest (data-layer + soft-delete regression tests)
```

`VITE_AI_PROXY_URL` (optional) overrides where the client sends AI report requests — defaults to the same-origin relative `/api`, correct once deployed alongside the `api/` functions on Vercel. Only needed locally to point at a stand-in server during development.
